How a change gets in

CONTRIBUTING.md →

  1. Start with an issue

    Every change, bug fix or feature, starts as an issue that says why. Use the bug report or feature request template.

  2. One issue, one small pull request

    A PR references its issue and changes the code for one reason. Over about 500 lines or 10 files, split it.

  3. Bring tests

    Unit or functional tests come with the code; if they can't, the PR says why.

  4. Review and CI

    A maintainer reviews, and the CI builds and tests the PR (see below).

How the code is organised

pyphare/Python package: simulation setup, running, post-processing.
↓
src/python3/pybind11 bindings, one module per dimension and interpolation order.
↓
src/simulator/Assembles everything and owns the time loop.
↓
src/amr/Everything that talks to SAMRAI: patch data, refinement, level messengers, solvers.
↓
src/core/Physics and numerics, with no SAMRAI dependency: grid layout, fields, particles, pusher, Faraday, Ampère, Ohm, MHD numerics.

Lower layers never include upper ones. Most code is header-only C++ templates on dimension and interpolation order.

How the CI checks a PR

GitHub Actions

Builds PHARE and runs the test suite on Ubuntu, plus CodeQL static analysis.

TeamCity at LPP

Builds every PR with gcc and with clang (with AddressSanitizer), with and without a pre-built SAMRAI, and runs about 1,500 tests. Nightly and weekly jobs on master add performance and coverage runs.

Weekly activity

Every Monday a report shows the past week's issues, PRs, reviews and CI results: activity reports.
